# Deployment

How Faroz runs outside the team laptop. **Now:** Render, for the defense on 2 Nov 2026 ([D-31](../01-architecture/decisions.md), proposed). **Later:** a VPS (MVPS) with the same build and start commands. Everything below is prepared in the repository; creating accounts, choosing paid plans and pressing "Deploy" is the owner's step.

## What runs where

| Piece | Render service | Notes |
| --- | --- | --- |
| PostgreSQL (Render's default version) | `faroz-db` (free) | Deleted by Render 30 days after creation on the free plan; the paid plan keeps it and has backups |
| API (NestJS) | `faroz-api` (web, free) | `https://faroz-api.onrender.com`; health: `/api/v1/health`; Socket.IO at `/realtime` |
| Website (Next.js) | `faroz-web` (web, free) | `https://faroz-web.onrender.com`; forwards `/api/v1/*` to the API, so session cookies belong to the site |
| Android app | EAS Build (Expo) | APK built with `eas.json` profile `preview`, pointed at the Render API; offered on the site at `/download` |

**Real-time on two domains.** The browser's cookie lives on the site's domain, but sockets connect straight to the API (rewrites cannot carry WebSockets). The site therefore fetches a two-minute ticket (`POST /api/v1/realtime/ticket`, through its own origin) and sends it as `auth.token`; the API accepts it only while that session is live ([api-conventions](../03-api/api-conventions.md)).

## Render: first deployment (about 20 minutes)

1. Push the branch named in `render.yaml` (`feat/faroz-platform`) to GitHub.
2. Render → **New → Blueprint** → connect the GitHub repository → Render reads [`render.yaml`](../../render.yaml) and shows the database and two services → **Apply**.
3. Wait for both builds. The API start command runs, in order: `prisma migrate deploy`, the learning content (`db:seed`), and on the very first start the demo data (`db:seed:demo`), then the API ([`apps/api/scripts/render-start.mjs`](../../apps/api/scripts/render-start.mjs)).
4. **Check the addresses.** If Render gave a service a different URL (the name was taken), set `WEB_ORIGIN` on `faroz-api` and `NEXT_PUBLIC_API_URL` on `faroz-web` to the real ones and redeploy both (the site reads `NEXT_PUBLIC_API_URL` at build time).
5. Open `https://faroz-web.onrender.com/ru` and run the checks below.

## Environment

API (`faroz-api`). The server refuses to start in production without `SESSION_SECRET`, with a non-https or localhost `WEB_ORIGIN`, or with `RATE_LIMIT=off`.

| Variable | Render value | Meaning |
| --- | --- | --- |
| `NODE_ENV` | `production` | Secure cookies, no localhost origins, the checks above |
| `DATABASE_URL` | from `faroz-db` | Internal connection string |
| `SESSION_SECRET` | generated by Render | Signs tickets and encrypts two-factor secrets; keep it stable (changing it signs everyone out of two-factor setups) |
| `WEB_ORIGIN` | the site's https address | CORS, cookie-write Origin check, reset links |
| `ALLOWED_ORIGINS` | — | Extra site addresses, comma separated (e.g. a custom domain) |
| `TRUST_PROXY` | `on` | Client address from `X-Forwarded-For` (rate limits per visitor, not per proxy) |
| `DEMO_LOGINS` | `on` | Demo learners and staff without passwords. **Turn `off` for real users** |
| `SEED_ON_START` | `demo` | `off` · `content` · `demo` (demo data only on the first start) · `reset-demo` (resets demo learners on every start; use once before the defense, then back to `demo`) |
| `PUSH_DELIVERY` / `PUSH_SCHEDULER` | `log` / `off` | Push stays local until EAS/Firebase credentials exist ([mobile story](../stories/2026-10-31-mobile-app.md)) |
| `TZ` | `Asia/Dushanbe` | Dates in notifications and daily windows |
| `PORT` | set by Render | The API listens on it (`API_PORT` wins if set) |

Website (`faroz-web`): `NEXT_PUBLIC_API_URL` (the API's https address + `/api/v1`; read at build time, so changing it needs a redeploy), `ANDROID_APK_URL` (optional, https link to the APK) and `ANDROID_APP_VERSION` (optional; both read on each request, Render restarts the service when they change).

## Android app for the Render API

1. Install the EAS CLI and sign in: `npm i -g eas-cli`, `eas login` (free Expo account).
2. In `apps/mobile`: `eas init` (links the project and writes `extra.eas.projectId` into `app.json`; commit it).
3. `eas build --platform android --profile preview` → an APK built against `https://faroz-api.onrender.com/api/v1` (change it in `eas.json` if the address differs).
4. Copy the build's download link (or attach the APK to a GitHub release) and set it as `ANDROID_APK_URL` on `faroz-web`, plus `ANDROID_APP_VERSION` (e.g. `0.1.0`). `/download` then shows the button.
5. Push notifications additionally need Firebase (FCM v1 key uploaded to EAS) and `PUSH_DELIVERY=expo` on the API.

## Checks after each deployment

- [ ] `https://faroz-api.onrender.com/api/v1/health` answers `{"status":"ok",…}`.
- [ ] The site opens in ru, tg, en; dark and light; `/download` shows the right state.
- [ ] Demo learner: diagnostic, practice, result; teacher: groups and a live board; center: totals only.
- [ ] Live exam: the teacher's board updates when the learner answers (sockets work across the two domains).
- [ ] Chat between the teacher and a learner delivers live.
- [ ] Mobile APK: sign in as the demo learner; lessons load; an offline lesson opens in airplane mode.

## Free plan behaviour (plan around it on the defense day)

- Services sleep after ~15 minutes without traffic; the first request then takes up to a minute. Open the site and the API health URL 5 minutes before presenting, and keep a tab open.
- The free database expires after 30 days. Export with `pg_dump` before then, or move to the paid plan or the VPS.
- One API instance: in-memory rate limits and call registry are per instance (fine for one instance).
- Free instances have 512 MB of memory. If a build fails with "out of memory" (most likely the site's `next build`), add `NODE_OPTIONS=--max-old-space-size=460` to that service or use the Starter plan.

## Updates and rollback

- Every push to the branch redeploys (Render auto-deploy). Migrations run on start; they are additive and forward-only, so a rollback of the code keeps the newer schema (still compatible).
- Roll back in Render → service → **Events** → redeploy an earlier commit.
- Fresh demo data before a presentation: set `SEED_ON_START=reset-demo`, redeploy, check, set it back to `demo`.

## Later: VPS (MVPS)

Same commands on one server: Node 24, pnpm (corepack), PostgreSQL 18, a reverse proxy with HTTPS (Caddy or nginx + Let's Encrypt), and two systemd services (or Docker):

- Build: `corepack enable && pnpm install --frozen-lockfile && pnpm prep && pnpm --filter @nuvora/api build && pnpm --filter @nuvora/web build`
- API: `cd apps/api && node scripts/render-start.mjs` with the API variables above (`TRUST_PROXY=on` behind the proxy).
- Site: `pnpm --filter @nuvora/web start` with `NEXT_PUBLIC_API_URL`.
- Proxy: the site's domain → port 3000; the API's domain (or `/realtime` and `/api/v1` paths) → the API port, with WebSocket upgrades enabled.
- Add nightly `pg_dump` backups and turn `DEMO_LOGINS` off once real users sign up.
